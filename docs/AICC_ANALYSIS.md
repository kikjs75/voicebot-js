# CTI 협력사와 소통할 때 필요한 SIP/RTP 개념 설명해줘                                                                                                                                                      
```
  ---
  1. 역할 분리부터 이해하기

  전화 한 통 = 신호 + 음성  (완전히 별개의 프로토콜)

  ┌─────────────────────────────────────────────────┐
  │  SIP  — "전화 연결/종료" 신호 담당              │
  │         "나 전화할게" "받아" "끊어"             │
  │         텍스트 기반, 제어 채널                  │
  ├─────────────────────────────────────────────────┤
  │  RTP  — "실제 음성 데이터" 전송 담당            │
  │         소리 바이트를 실시간으로 흘려보냄        │
  │         UDP 기반, 미디어 채널                   │
  └─────────────────────────────────────────────────┘

  비유:
    SIP = 전화기 버튼 (발신/수신/종료)
    RTP = 수화기로 전달되는 목소리

  ---
  2. SIP — 세션 제어 프로토콜

  2-1. SIP 메시지 흐름 (전화 한 통)

  고객 (UA)              PBX / SIP Proxy          음성봇 서버
      │                        │                       │
      │──── INVITE ────────────▶│                       │
      │     (전화 걸게)         │──── INVITE ──────────▶│
      │                        │     (음성봇에 연결)    │
      │                        │◀─── 100 Trying ───────│
      │◀─── 100 Trying ────────│                       │
      │                        │◀─── 180 Ringing ──────│ (벨 울림)
      │◀─── 180 Ringing ───────│                       │
      │                        │◀─── 200 OK ───────────│ (수신)
      │◀─── 200 OK ────────────│                       │
      │──── ACK ───────────────▶│──── ACK ─────────────▶│
      │                        │                       │
      │ ←═══════════ RTP 음성 스트림 시작 ════════════▶ │
      │                        │                       │
      │──── BYE ───────────────▶│──── BYE ─────────────▶│ (종료)
      │◀─── 200 OK ────────────│◀─── 200 OK ───────────│

  2-2. SIP 핵심 메서드

  ┌─────────┬──────────────────┬──────────────────────┐
  │ 메서드  │       역할       │      발생 시점       │
  ├─────────┼──────────────────┼──────────────────────┤
  │ INVITE  │ 세션 시작 요청   │ 전화 걸 때           │
  ├─────────┼──────────────────┼──────────────────────┤
  │ ACK     │ INVITE 응답 확인 │ 3-way handshake 완료 │
  ├─────────┼──────────────────┼──────────────────────┤
  │ BYE     │ 세션 종료        │ 전화 끊을 때         │
  ├─────────┼──────────────────┼──────────────────────┤
  │ CANCEL  │ 연결 전 취소     │ 수신 전 끊을 때      │
  ├─────────┼──────────────────┼──────────────────────┤
  │ OPTIONS │ 기능 조회        │ 상태 확인            │
  ├─────────┼──────────────────┼──────────────────────┤
  │ REFER   │ 전환 요청        │ 상담사에게 넘길 때   │
  └─────────┴──────────────────┴──────────────────────┘

  2-3. CTI 협력사 대화에서 나오는 SIP 용어

  UA (User Agent)     → 전화기 또는 소프트폰 (끝단 장치)
  SIP Proxy           → 중간 라우터 역할 PBX
  SDP (Session Desc.) → INVITE 안에 포함, 미디어 협상 정보
                        (어떤 코덱 쓸지, 어떤 IP/포트로 RTP 받을지)

  INVITE 메시지 내부 SDP 예시:
  ────────────────────────────
  v=0
  o=voicebot 1234 5678 IN IP4 192.168.1.10
  s=VoiceBot Session
  c=IN IP4 192.168.1.10      ← RTP 받을 IP
  t=0 0
  m=audio 20000 RTP/AVP 0 8  ← 포트 20000, 코덱 0(G.711μ) 8(G.711a)
  a=rtpmap:0 PCMU/8000
  a=rtpmap:8 PCMA/8000
  ────────────────────────────
       └─ 이 협상 결과가 RTP 설정에 그대로 반영됨

  ---
  3. RTP — 실시간 음성 전송 프로토콜

  3-1. RTP 패킷 구조

  ┌──────────────────────────────────────────────────────┐
  │                   RTP 패킷                           │
  │                                                      │
  │  ┌──────┬──────┬────────────┬──────────────────────┐ │
  │  │  V   │  PT  │  Sequence  │     Timestamp        │ │
  │  │ (2b) │ (7b) │   (16b)    │       (32b)          │ │
  │  ├──────┴──────┴────────────┴──────────────────────┤ │
  │  │              SSRC (32b) — 송신자 식별            │ │
  │  ├─────────────────────────────────────────────────┤ │
  │  │         Payload — 실제 음성 데이터 (PCM 등)      │ │
  │  └─────────────────────────────────────────────────┘ │
  └──────────────────────────────────────────────────────┘

  V         : RTP 버전 (항상 2)
  PT        : Payload Type → 코덱 종류 (0=G.711μ, 8=G.711a)
  Sequence  : 패킷 순번 → 유실/순서 역전 감지
  Timestamp : 재생 시점 동기화 → 음성 끊김 방지
  SSRC      : 동시 통화 여러 개일 때 구분자

  3-2. 오디오 코덱 비교 (가장 자주 나오는 협상 항목)

  ┌─────────────────────────────────────────────────────────────┐

  3-3. RTP가 UDP를 쓰는 이유

  TCP vs UDP — 음성에서 UDP를 선택하는 이유

  TCP                              UDP
  ─────────────────────────────    ─────────────────────────────
  패킷 유실 → 재전송 대기          패킷 유실 → 그냥 넘어감
  순서 보장                        순서 보장 없음 (직접 처리)
  지연 발생 가능                   지연 최소

  음성 통화에서 패킷 1개 유실 = 20ms 잡음
  재전송 기다리면 = 수백ms 끊김 (훨씬 나쁨)

  → 유실을 감수하고 낮은 지연을 선택 = UDP + RTP
     순서 역전은 Sequence Number로 직접 처리

  4. DTMF — 버튼 입력 처리

  고객이 "1번 누르세요" → "1" 키 입력 처리 방법

  방법 1: Inband DTMF
    음성 주파수(톤)를 RTP 스트림 안에 포함
    → STT가 오인식 가능, 권장하지 않음

  방법 2: RFC 2833 (Out-of-band DTMF) — 권장
    별도 RTP 패킷 타입(PT=101)으로 분리 전송
    → 음성과 완전히 분리, 신뢰성 높음

  방법 3: SIP INFO
    SIP 시그널링 채널로 전송
    → 실시간성 약간 떨어짐

  CTI 협력사와 협의 시 반드시 확인:
    "DTMF는 RFC 2833로 처리하시나요?"

  ---
  변환이 필요한 이유부터

  PBX가 보내주는 것         RTZR STT가 원하는 것
  ─────────────────         ─────────────────────
  G.711 μ-law               PCM (raw)
  8,000Hz                   16,000Hz
  8bit/sample               16bit/sample
  압축된 형태               비압축 형태

  → 2단계 변환 필요:
    ① G.711 디코딩  (압축 해제: 8bit → 16bit)
    ② 업샘플링     (8kHz → 16kHz, 샘플 2배로 늘리기)

  ---
  변환 단계 시각화

  PBX에서 받은 G.711 패킷 (20ms, 160 bytes)

    [A4][B2][C8][D1]...   ← 8bit μ-law 압축 샘플, 160개

             ① G.711 디코딩
             (로그 스케일 → 선형 스케일)
                 ↓

    [0x0A40][0x1B20]...   ← 16bit PCM 샘플, 160개 (8kHz)

             ② 업샘플링
             (샘플 사이에 보간값 삽입)
                 ↓

    [0x0A40][0x12B0][0x1B20][0x1DC0]...  ← 16bit PCM 샘플, 320개 (16kHz)
             └─보간─┘        └─보간─┘

  ---
  실제 구현

  변환 로직을 별도 유틸 클래스로 분리합니다.

  // src/main/java/com/voicebot/audio/AudioConverter.java

  public class AudioConverter {

      // ① G.711 μ-law → 16bit PCM (8kHz)
      public static short[] decodeMuLaw(byte[] muLawBytes) {
          short[] pcm = new short[muLawBytes.length];
          for (int i = 0; i < muLawBytes.length; i++) {
              pcm[i] = muLawToPcm(muLawBytes[i]);
          }
          return pcm;
      }

      private static short muLawToPcm(byte muLaw) {
          int uLaw = (~muLaw) & 0xFF;
          int exponent = (uLaw >> 4) & 0x07;
          int mantissa = uLaw & 0x0F;
          int sample = (mantissa << 3) + 132;
          sample <<= exponent;
          sample -= 132;
          return (short) ((uLaw & 0x80) != 0 ? -sample : sample);
      }

      // ② 8kHz → 16kHz 업샘플링 (선형 보간)
      public static short[] upsample8to16(short[] pcm8k) {
          short[] pcm16k = new short[pcm8k.length * 2];
          for (int i = 0; i < pcm8k.length - 1; i++) {
              pcm16k[i * 2] = pcm8k[i];
              pcm16k[i * 2 + 1] = (short) ((pcm8k[i] + pcm8k[i + 1]) / 2); // 중간값
          }
          // 마지막 샘플 처리
          pcm16k[pcm16k.length - 2] = pcm8k[pcm8k.length - 1];
          pcm16k[pcm16k.length - 1] = pcm8k[pcm8k.length - 1];
          return pcm16k;
      }

      // short[] → byte[] 변환 (RTZR에 byte[]로 전송)
      public static byte[] toBytes(short[] samples) {
          byte[] bytes = new byte[samples.length * 2];
          for (int i = 0; i < samples.length; i++) {
              bytes[i * 2]     = (byte) (samples[i] & 0xFF);
              bytes[i * 2 + 1] = (byte) ((samples[i] >> 8) & 0xFF);
          }
          return bytes;
      }

      // 한 번에 변환 (G.711 μ-law → PCM 16kHz byte[])
      public static byte[] convertMuLawTo16kPcm(byte[] muLawBytes) {
          short[] pcm8k  = decodeMuLaw(muLawBytes);
          short[] pcm16k = upsample8to16(pcm8k);
          return toBytes(pcm16k);
      }
  }

                (10+30)/2  (30+20)/2  (20+40)/2

  ---
  코드는 딱 이것만

  // 1. G.711 압축 해제
  short[] pcm8k = decodeMuLaw(chunk);

  // 2. 8kHz → 16kHz (샘플 2배로 늘리기)
  short[] pcm16k = upsample(pcm8k);

  // 3. RTZR로 전송
  sink.tryEmitNext(toBytes(pcm16k));

  ---
  어디에 추가하냐

  음성 청크 들어옴 (G.711)
          ↓
    [변환] ← 여기 한 줄 추가
          ↓
  RTZR로 전달 (PCM 16kHz)

  기존 코드에서 sink.tryEmitNext(chunk) 한 줄 앞에
  chunk = 변환(chunk) 만 끼워 넣으면 끝입니다.

  ---
  현실적인 이야기

  사실 이 변환을 우리가 직접 짜는 경우는 드뭄

  더 흔한 방법:
    ① CTI 협력사에 요청
       "16kHz PCM으로 변환해서 주세요" → 협력사가 처리

    ② 미디어 서버 사용
       Asterisk, FreeSWITCH 같은 미디어 서버가 중간에서 변환

    ③ 직접 구현
       위 코드처럼 우리가 변환 (협력사가 안 해줄 때)

  ---
  결론: 변환 자체는 어렵지 않고, 협력사 미팅에서 "16kHz PCM으로 주실 수 있나요?" 한 마디면 해결되는 경우가 대부분입니다.

  ---
  RTZR STT 연동 스펙

  ---
  전체 흐름 한눈에

  우리 서버                         RTZR 서버
  ────────────────                  ─────────────────

  ① 토큰 발급 요청  ──────────────▶  /v1/authenticate
                   ◀──────────────  access_token 반환

  ② WebSocket 연결  ──────────────▶  /v1/transcribe:streaming
                                      (연결 시 음성 파라미터 전달)

  ③ 음성 청크 전송  ──────────────▶  binary frame 계속 전송
                   ◀──────────────  중간 결과 (isFinal=false)
                   ◀──────────────  중간 결과 (isFinal=false)

  ④ EOS 전송        ──────────────▶  "EOS" 문자열
                   ◀──────────────  최종 결과 (isFinal=true)

  ⑤ 연결 종료

  ---
  ① 토큰 발급

  매번 음성 전송 전에 토큰을 미리 받아둬야 함

  POST https://openapi.vito.ai/v1/authenticate
  Body: client_id=xxx&client_secret=yyy

  응답:
  {
    "access_token": "eyJhbGci...",
    "expire_at": 1719000000      ← 만료 시각 (Unix timestamp)
  }

  우리 코드의 전략:
  }

  우리 코드의 전략:
    - 앱 시작 시 즉시 발급 (@PostConstruct)
    - 5분마다 만료 시각 체크 (@Scheduled)
    - 만료 10분 전이면 미리 갱신
    → 통화 중에 토큰이 만료되는 상황 방지

  ---
  ② WebSocket 연결 URL 파라미터

  wss://openapi.vito.ai/v1/transcribe:streaming
    ?sample_rate=8000          ← 음성 샘플레이트 (8000 or 16000)
    &encoding=LINEAR16         ← 음성 포맷 (PCM 16bit)
    &use_itn=true              ← 숫자 변환 ("삼만원" → "30,000원")
    &use_disfluency_filter=true ← 말 더듬 제거 ("어... 그... 환불" → "환불")
    &use_profanity_filter=false ← 욕설 필터 (콜센터는 보통 false)
    &use_punctuation=false     ← 문장부호 자동 삽입

  헤더:
    Authorization: Bearer {access_token}

  ---
  ③ 음성 전송 방식

  연결 후 음성 청크를 binary frame으로 계속 전송

  우리 코드:
    audioStream.subscribe(
        chunk -> ws.send(ByteString.of(chunk))  ← 청크 올 때마다 바로 전송
    )

  주의사항:
    - 포맷: PCM (raw bytes, 헤더 없음)
    - WAV 파일이면 앞 44바이트 헤더 제거 후 전송
    - 청크 크기: 4096 bytes 권장 (약 250ms 분량)

  ---
  ④ 응답 메시지 형식

  // 중간 결과 (말하는 중)
  {
    "final": false,
    "alternatives": [
      { "text": "안녕하세요 환불" }
    ]
  }

  // 최종 결과 (발화 완료)
  {
    "final": true,
    "alternatives": [
      { "text": "안녕하세요 환불 문의드립니다" }
    ]
  }

  우리 코드의 처리:
    isFinal=false → emitter.next()  중간 결과 흘려보냄
    isFinal=true  → emitter.next()  최종 결과 흘려보내고
                    ws.close()      WebSocket 닫음
                    emitter.complete() 스트림 종료

  ---
  ⑤ EOS — 발화 종료 신호

  EOS = End Of Stream

  고객이 말을 멈췄을 때:
    ws.send("EOS")  ← 문자열로 전송

  RTZR이 EOS를 받으면:
    → 지금까지 받은 음성을 최종 처리
    → isFinal=true 결과 반환
    → 연결 종료

  우리 코드:
    audioStream.subscribe(
        chunk -> ...,       // 음성 청크
        error -> ...,       // 오류
        () -> ws.send("EOS") // 스트림 완료 시 EOS 전송
    )

  System Prompt — 가장 중요한 설계 포인트

  System Prompt = Claude에게 주는 역할/규칙 지침서

  우리 코드의 System Prompt:
  ────────────────────────────────────────────────
  당신은 한국어 콜센터 AI 상담원입니다.
  고객 발화를 분석하고 반드시 아래 JSON 형식으로만 응답하세요.
  {"intent": "의도", "response": "상담 응답"}
  규칙:
  - intent: 고객 의도 한 단어 (환불/배송문의/기술지원/요금문의/예약/기타)
  - response: 2~3문장 이내 자연스러운 구어체 한국어
  - 마크다운(#, **, -), 이모지, 특수문자 사용 금지
  - JSON 외 다른 텍스트 출력 금지
  ────────────────────────────────────────────────

  왜 JSON으로 강제하나?
    TTS에 넘기기 전에 response만 꺼내야 함
    intent는 다음 시나리오 분기에 써야 함
    → 파싱 가능한 구조화된 형식 필수

  전화 한 통 = Messages 배열이 쌓이는 과정

  [
    { "role": "user", "content": "환불하고 싶어요" }
  ]

  [

  ]

  [
    { "role": "user",      "content": "환불하고 싶어요" },

    { "role": "user",      "content": "12345입니다" },

    { "role": "user",      "content": "단순변심이요" }    ← 새 발화 추가
  ]

  ```json

  ### 과금 구조 — 토큰 단위

  토큰 = 단어보다 작은 단위
    "안녕하세요" ≈ 3~4 토큰
    영어 1단어 ≈ 1 토큰

  과금:
    input_tokens  (우리가 보낸 것) × 단가
    output_tokens (Claude가 응답한 것) × 단가

  콜센터에서 토큰이 쌓이는 구조:
    System Prompt  ≈ 150 토큰  (매 요청마다 포함)
    대화 이력      ≈ 발화 횟수 × 50 토큰씩 누적
    응답           ≈ 50~100 토큰

  → 통화가 길어질수록 input_tokens 증가
  → 대화 이력을 적절히 잘라내는 전략 필요
     (예: 최근 10턴만 유지)

  1. 코드에서 바로 보이는 협의 항목

  wss://openapi.vito.ai/v1/transcribe:streaming
    ?sample_rate=8000           ① 샘플레이트
    &encoding=LINEAR16          ② 인코딩 (음성 포맷)
    &use_itn=true               ③ 숫자 변환 방식
    &use_disfluency_filter=true ④ 말 더듬 제거
    &use_profanity_filter=false ⑤ 욕설 필터
    &use_punctuation=false      ⑥ 문장부호 삽입

  ① sample_rate — 이미 알고 있는 것

  PBX가 8kHz로 주면 → 8000
  16kHz로 받으면   → 16000
  RTZR이 지원하는 값 범위 확인 필요

  ② encoding — 음성 포맷

  LINEAR16 = PCM 16bit (우리 현재 설정)
  FLAC     = 무손실 압축
  MULAW    = G.711 μ-law (PBX 표준)

  CTI 협력사가 어떤 포맷으로 주느냐에 따라 결정
  → "LINEAR16 그대로 받을 수 있나요?"

  ③ use_itn — 숫자 변환

  true  → "삼만원" → "30,000원"
  false → "삼만원" 그대로

  콜센터에서는 보통 true
  주문번호, 금액, 전화번호 처리에 영향

  ④ use_disfluency_filter — 말 더듬 제거

  true  → "어... 그... 환불이요" → "환불이요"
  false → "어... 그... 환불이요" 그대로

  Claude 프롬프트 전달 전에 걸러주므로 true 권장

  ⑤ use_profanity_filter — 욕설 필터

  true  → 욕설을 *** 처리
  false → 그대로 전달 (우리 현재 설정)

  콜센터는 고객 발화 그대로 기록해야 하므로 false

  ⑥ use_punctuation — 문장부호

  true  → "안녕하세요. 환불 문의입니다."
  false → "안녕하세요 환불 문의입니다" (우리 현재 설정)

  TTS로 바로 넘기는 구조라면 false가 낫다
  (Claude가 응답 생성할 때 영향 없음)

⏺ SLA (Service Level Agreement)

  서비스 수준 협약 — 업체가 "우리 서비스는 이 정도는 보장할게요"라고 계약서에 적는 약속입니다.

  ---
  콜센터에서 중요한 SLA 항목 3가지

  ① 가용성 (Availability)
     "1년 중 서버가 얼마나 살아있나?"

     99.9%  → 1년에 약 8시간 다운 허용
     99.99% → 1년에 약 50분 다운 허용

     콜센터는 24시간 운영이라 99.9% 이상 요구


  ② 응답 시간 (Latency)
     "음성 보내면 텍스트가 얼마나 빨리 오나?"

     우리 목표: STT < 1,000ms
     → 업체에게 "1초 이내 보장 가능한가요?" 확인


  ③ 장애 대응 시간 (RTO)
     "서버 죽으면 얼마 안에 복구해주나?"

     RTO 1시간 → 장애 나면 1시간 내 복구 보장

  24000  → 고음질

  2. 코드에는 없지만 협의해야 할 것

  ⑤ 음성 주입 방식 — 가장 중요

  TTS가 음성 바이트를 만들었다고 끝이 아님
  이걸 고객 귀에 어떻게 들려주냐가 핵심

  방법 A: URL 방식 (간단)
    우리가 음성 파일을 URL로 제공
    → PBX가 URL 접근해서 가져가 재생
    → 우리는 파일 서버 역할만 하면 됨

  방법 B: RTP 직접 주입 (복잡)
    우리가 직접 음성 패킷을 PBX로 전송
    → RTP 스트리밍 구현 필요
    → 지연시간 최소화 가능

  → CTI 협력사에게 먼저 물어봐야 할 것:
    "TTS 음성을 어떻게 전달받고 싶으세요?"

  ⑥ TTFB (첫 음성까지 걸리는 시간)

  TTFB = Time To First Byte
       = 텍스트 보내고 음성 첫 바이트 오기까지

  현재 우리 구조:
    LLM 응답 완성 → TTS 요청 → 음성 전체 받음 → 재생
    = 전체 음성이 다 올 때까지 고객은 침묵을 듣게 됨

  개선 방법:
    스트리밍 TTS 지원 여부 확인
    → 문장 단위로 쪼개서 앞부분부터 재생 시작
    → "안녕하세요" 합성되는 동안 "환불" 합성 준비

  협의 포인트:
    "스트리밍 응답 지원하나요?"
    "TTFB가 보통 얼마나 되나요?"

  ⑦ SSML 지원 여부

  SSML = 음성 표현 마크업 언어

  지원하면 이런 것들이 가능:
    <break time='500ms'/>      → 자연스러운 쉼
    <emphasis>중요</emphasis>  → 강조
    <prosody rate='slow'>      → 천천히 읽기
    <say-as interpret-as='digits'>1588</say-as>  → 숫자 읽기

  콜센터에서 유용한 케이스:
    "주문번호는 1-2-3-4-5 입니다" (숫자 하나씩 읽기)
    "잠시만요." (쉼 추가)
    노령 고객 대응 시 천천히 읽기

  ⑧ 캐싱 전략

  고정 문구는 매번 TTS 호출할 필요 없음

  캐싱 후보:
    "안녕하세요, OO 고객센터입니다"
    "잠시만 기다려 주세요"
    "감사합니다"
    "연결해 드리겠습니다"

  현재 코드에 캐싱 없음
  → Redis에 text를 key로 캐싱하면
    비용 절감 + 응답속도 향상

  협의 포인트:
    "동일 텍스트 반복 요청 시 캐싱 지원하나요?"
    (업체 측에서 캐싱해주는 경우도 있음)
